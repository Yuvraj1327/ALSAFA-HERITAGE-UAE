# Itemised shop expenses, supplier integration and payment-based cash

Migration: `database/migrations/0021_itemised_shop_expenses.sql`. Supersedes `docs/OWNER_EDITS_PDF_OTHER_EXPENSES.md`
(the free-text "Other" JSON list is now a frozen legacy record).

## 1. What changed for the user

| Area | Before | Now |
|---|---|---|
| Daily Report | one "Shop Expenses" total + optional free-text "Other" items | any number of **itemised rows**: Category, Description, Amount, Remarks, Supplier, Payment Status, Payment Account, Amount Paid, Outstanding |
| Categories | none (Other only) | Food, Raw Material, Stationery, Repairs & Maintenance, Petrol, Other. **Savings is not a category**: it keeps its own field |
| Payment | every shop expense reduced cash on the report date | **Paid** (in full, from Cash/ENBD/ADCB), **Unpaid** (needs a supplier, moves nothing), **Partial** (needs a supplier; only the part paid moves money) |
| Suppliers | dues entered by hand | an Unpaid/Partial/supplier-linked row creates the supplier **due** (and the **payment** for what was paid) automatically, traceable to the row |
| Expenses & Savings page | "Other Expenses" tab | **Shop expenses** tab: itemised history, category-, branch-, date-, supplier- and status-wise views, filters |
| Dashboard / Reports | one shop expense figure | Total / Paid / Unpaid / Partial / Outstanding shop expenses, Supplier Outstanding, Net Cash, ENBD & ADCB; 4 new reports; category/status filters |

Head Office Expenses are untouched (own table, own 7 categories, own workflow).

## 2. Data model

`daily_report_expenses` (one row per expense row; immutable except the void columns):
`report_id, branch_id, expense_date, line_no, category, description, amount (>0), remarks, supplier_id, supplier_name (snapshot),
payment_status, payment_account, amount_paid, outstanding (= amount − amount_paid, generated), is_legacy, void columns`.

Database-enforced rules (CHECK constraints): category in the six (+ `Other (Legacy)` for migrated rows only);
Paid ⇒ `amount_paid = amount` and an account; Unpaid ⇒ `amount_paid = 0`, no account; Partial ⇒ `0 < amount_paid < amount` and an account;
Unpaid/Partial ⇒ a supplier; legacy rows are always Paid, no supplier.

`supplier_entries.source_expense_id` links a ledger row to its expense row. A partial unique index
`(source_expense_id, kind) WHERE source_expense_id IS NOT NULL AND voided_at IS NULL` makes a second due or second payment for one row impossible.

`daily_reports.shop_expenses` stays a stored column but is now **derived and enforced**:

    shop_expenses = SUM(active expense rows) + shop_savings        (deferred constraint trigger, checked at commit)

`daily_reports.other_expenses` (jsonb) is kept as a read-only legacy record (a trigger refuses any change; new reports carry `[]`).
The old validation trigger `dr_validate_other` was replaced by itemised validation (`app.parse_report_expenses`) and by the freeze trigger.

## 3. Calculations (single source: `backend/app/core/calculations.py` + `app_cash_bank_ledger()`)

    Itemised expenses      = Σ row.amount                       (credit purchases count when incurred)
    Total Shop Expenses    = Itemised expenses + Savings
    Row outstanding        = amount − amount_paid
    Net cash (day/branch)  = Cash Received − Σ amount_paid (rows paid from Cash) − Savings
    Sales Minus Expenses   = Total Sales − Shop Expenses (excl. savings) − Head Office Expenses (excl. savings)
    Supplier outstanding   = Opening + valid dues − valid payments

Cash / bank ledger (every balance is `opening + Σ signed ledger rows`; nothing is ever stored or overwritten):

| Account | Movements |
|---|---|
| Cash (per branch) | + gross cash received; − savings; − paid shop rows **without** a supplier paid in Cash; − supplier payments in Cash (incl. those generated by report rows, charged to the report's branch); − head-office cash; ± transfers |
| ENBD / ADCB | + collections to the receiving bank; − paid shop rows without a supplier paid from that bank; − supplier payments from that bank; − head-office payments; − cleared rental cheques; ± transfers; + POS settlements |
| POS Pending | opening + POS collections − POS settlements |

**No double counting:** a supplier-linked row's money leaves the account through exactly **one** ledger row — the generated
*Supplier payment* — never also through a shop-expense row. Non-supplier rows produce a *Shop expenses* ledger row.
Unpaid amounts and the unpaid part of Partial rows never touch an account. *Gross* cash received is unchanged (used for sales reconciliation).

## 4. Corrections (void-and-replace, atomic)

* **Submit** `public.submit_daily_report()`; **Owner edit** `public.edit_daily_report()` (new signature: no `shop_expenses`/`other_expenses`,
  takes `p_shop_savings` and `p_expenses jsonb`); **Owner void** `public.void_daily_report()`.
* Edit = in one transaction: lock → void the old rows and the supplier ledger rows they generated (reason recorded) → update the report →
  insert replacement rows and replacement ledger rows. Voided rows stay as history; `audit_log` records old/new values, actor, time and reason.
* A correction that would leave any supplier with a negative balance (because later payments exist) is refused as a whole.
* A generated supplier row cannot be voided on its own (`void_supplier_entry` refuses it): correct or void the report instead.
* Repeating an edit never duplicates ledger rows (new row ids; unique index on live source rows).
* Branch Users can submit, never edit or void. Branch-user direct INSERT into the lines or the ledgers is impossible (no grant).
* Supplier-linked rows are only accepted for dates after the opening-balance date (the ledger does not track earlier days).

## 5. Security (RLS and functions)

* `daily_report_expenses`: RLS on; SELECT for the Owner and for a Branch User on their own branch; **no** INSERT/UPDATE/DELETE grant for anyone.
* `submit_daily_report` / `edit_daily_report` / `void_daily_report` / `report_supplier_options` are `SECURITY DEFINER` with `SET search_path = public, pg_temp`;
  identity comes only from `auth.uid()`; a Branch User's branch must equal `app.branch_id()`; edit/void check `app.is_owner()` again inside.
  They take the same advisory lock (80801) as every other balance-affecting write.
* Branch Users cannot read `suppliers`. `report_supplier_options()` returns **id + name of active suppliers only** (no balances/terms/notes);
  the supplier name is snapshotted on the row so reports display without reading `suppliers`. Supplier create/update and all ledger writes stay Owner-only.
* No service-role credential is used or exposed; the backend connects as the restricted `app_api` role under RLS as before.

## 7. Historical migration (what 0021 does to existing data)

1. **Pre-flight (nothing changed yet):** every report must satisfy `Σ legacy "Other" items ≤ shop_expenses − shop_savings`.
   If not, the migration **stops** and lists the offending report ids.
2. **Backfill:** per report, one `Other (Legacy)` row per existing `other_expenses` item (description, amount, notes→remarks preserved) plus **one**
   row `Unitemised shop expenses (legacy balance)` for `shop_expenses − shop_savings − Σ items` (only if > 0). All are *Paid from Cash* — exactly how the old ledger
   deducted them. Voided reports get voided rows. Savings are untouched. No report row is modified; `other_expenses` stays as it was.
3. **Verification inside the migration:** Σ active legacy rows = Σ (shop_expenses − shop_savings) over active reports; every active report reconciles;
   otherwise the migration aborts. One audit row `migration-0021` records the counts.
4. Cash, ENBD, ADCB, POS, savings, branch cash and supplier balances are identical before/after (proved by `TestHistoricalMigration`).

After an **Owner edit** of a historical report, its `Other (Legacy)` rows open as `Other` (the legacy label is not a selectable category) and are saved
with the new category; the change is audited. Untouched reports keep `Other (Legacy)`.

## 8. Frontend

* Daily Report form / Owner edit dialog: add/remove rows, selects for category, status, supplier, account; Amount Paid (editable only for Partial) and
  Outstanding per row; live totals (itemised, + savings, total shop expenses, paid, outstanding); review dialog.
* Daily Reports table: *Expense Items* (opens the row list) and *Net Cash* columns; PDF lists the rows, supplier, status and net cash.
* Expenses & Savings → *Shop expenses* tab. Supplier detail marks generated rows "Daily report · category" (no Void button).
* Dashboard: "Shop expenses & suppliers" cards. Reports & Analytics: extra KPI cards, new reports/charts, category + status filters.
